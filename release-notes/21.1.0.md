The IntelliJ IDEA plugin now formats inside the IDE's own JVM, with no process to start for a file, and Optimize Imports sorts and removes imports as open-java-format does, so the IDE and the build agree on imports too. The output differs from 21.0.2 in a few narrow cases, listed under Formatter, so take this release with one reformatting run, in a commit of its own.

## IntelliJ IDEA plugin

- Reformat Code and Optimize Imports run the formatter inside the IDE's JVM: 124 ms for a file of 4,026 lines, and 9 ms to fix its imports once warm, where a JVM started for each file took 0.3 s to 1 s. The settings page offers three ways under **Run the formatter**: **In the IDE process**, the default, **In a separate JVM**, on the IDE's runtime, the project SDK or another JDK of the IDE, Java 21 or later, and **Native binary**. A project that had **Use native binary** ticked keeps it ([#223](https://github.com/openjavaformat/open-java-format/issues/223), [#259](https://github.com/openjavaformat/open-java-format/pull/259)).
- Inside the IDE, the javac of the IDE's runtime decides which syntax parses: Java 21 in IntelliJ IDEA 2024.2, Java 25 in 2026.3. A project with newer syntax chooses a separate JVM on a newer JDK. There are no VM options to edit: the plugin opens javac to the formatter alone. Where it cannot, **In the IDE process** is greyed out with the reason under it, and the plugin formats in a separate JVM ([#259](https://github.com/openjavaformat/open-java-format/pull/259)).
- The way to run is saved as `formatterMode` in `.idea/open-java-format.xml`. A plugin older than 21.1.0 that reads the file formats in a JVM of its own ([#259](https://github.com/openjavaformat/open-java-format/pull/259)).
- **Optimize Imports** removes unused imports and sorts the others as the command line does, and so do Reformat Code with "Optimize imports", Actions on Save and "Optimize imports" before a commit. Up to 21.0.2 the IDE's own optimizer laid them out by the IDE's settings, and the build sorted them again ([#222](https://github.com/openjavaformat/open-java-format/issues/222), [#255](https://github.com/openjavaformat/open-java-format/pull/255)).
- Imports the IDE inserts, by auto-import, Alt+Enter or completion, follow open-java-format's layout: single-class imports rather than `.*`, and the static imports first. A project whose `.editorconfig` sets code style properties for Java files keeps those instead ([#255](https://github.com/openjavaformat/open-java-format/pull/255)).
- With "Optimize imports on the fly", typing no longer waits for the formatter in IntelliJ IDEA 2024.2 to 2025.1. From 2025.2 the IDE optimizes imports on the fly, and with Alt+Enter, by its own optimizer, which never asks the plugin: it follows the layout above, but removes an unused `import a.b.*;`, which open-java-format keeps ([#253](https://github.com/openjavaformat/open-java-format/issues/253), [#267](https://github.com/openjavaformat/open-java-format/pull/267)).
- In a project that takes the formatter from its Gradle build, the plugin reads the formatter's version once and closes its jars, so on Windows a build or a cache cleanup no longer fails on a jar the IDE holds. A formatter jar without an `Implementation-Version` no longer fails every format with a `NullPointerException` ([#258](https://github.com/openjavaformat/open-java-format/issues/258), [#264](https://github.com/openjavaformat/open-java-format/pull/264)).
- With debug logging on for `#com.palantir.javaformat`, `idea.log` says how each format and import optimization ended and how long it took ([#265](https://github.com/openjavaformat/open-java-format/pull/265)).

## Formatter

- A line comment that starts with `//` and a no-break space, or another Unicode space such as the ideographic space of Japanese comments, keeps it, where a regular space used to go in front of it; code formatted before keeps that space. Two kinds of wrapped comment that changed again on a second run now settle on the first ([google/google-java-format#1530](https://github.com/google/google-java-format/pull/1530) by Liam Miller-Cushon; [#249](https://github.com/openjavaformat/open-java-format/issues/249), [#251](https://github.com/openjavaformat/open-java-format/pull/251)).
- A long string literal under a cast, as the enclosing expression of a qualified `.new` or as the qualifier of a method reference stays whole, as `--skip-reflowing-long-strings` leaves it. It used to fail the whole file with "Something has gone terribly wrong" ([#252](https://github.com/openjavaformat/open-java-format/issues/252), [#256](https://github.com/openjavaformat/open-java-format/pull/256)).
- A Unicode escape in whitespace or in a comment delimiter, and an ignorable character in an identifier or keyword, fail with an error at its line and column, where the error used to point nowhere useful. The output for accepted input does not change ([google/google-java-format#1527](https://github.com/google/google-java-format/pull/1527) by Liam Miller-Cushon; [#244](https://github.com/openjavaformat/open-java-format/issues/244), [#246](https://github.com/openjavaformat/open-java-format/pull/246)).
- A stray `;` between imports fails with `extraneous semicolon` at its line, not with "Imports not contiguous" for the whole file ([google/google-java-format#1528](https://github.com/google/google-java-format/pull/1528) by Liam Miller-Cushon; [#245](https://github.com/openjavaformat/open-java-format/issues/245), [#248](https://github.com/openjavaformat/open-java-format/pull/248)).
- The layout allocates a sixth less, and a file with no long string to reflow skips that work; the output does not change ([#250](https://github.com/openjavaformat/open-java-format/issues/250), [#254](https://github.com/openjavaformat/open-java-format/pull/254), [#269](https://github.com/openjavaformat/open-java-format/pull/269)).

Javadoc formatting, which only the `formatJavadoc` option of the API turns on; the command line and the plugins leave Javadoc as it is:

- The `<p>` tags that end a comment are dropped, and a comment that then fits on one line becomes a one-liner ([#237](https://github.com/openjavaformat/open-java-format/issues/237), [#247](https://github.com/openjavaformat/open-java-format/pull/247)).
- A `<div>` after a blank line gets no `<p>` in front of it, which doclint reported as an empty `<p>` tag ([#268](https://github.com/openjavaformat/open-java-format/issues/268), [#270](https://github.com/openjavaformat/open-java-format/pull/270)).

## Command line, build plugins and Eclipse

- Formatting ranges, with `--lines`, `--offset` and `--length` or `--character-ranges`, leaves the imports alone, unused ones too, and reflows long strings only in the code the ranges rewrite. `formatDiff`, Eclipse and IntelliJ IDEA format ranges the same way ([#219](https://github.com/openjavaformat/open-java-format/issues/219), [#220](https://github.com/openjavaformat/open-java-format/pull/220), [#233](https://github.com/openjavaformat/open-java-format/pull/233), [#234](https://github.com/openjavaformat/open-java-format/pull/234)).
- The Maven plugin and the Spotless step write what the command line writes; in 3,865 files that changes one. A file with a stray `;` between imports, which they used to drop, now fails as on the command line ([#220](https://github.com/openjavaformat/open-java-format/pull/220)).
- `formatDiff` on the JVM reflows long strings as it does with the native binary, and no longer fails with "git diff took too long to terminate" on a diff larger than 64 KB ([#232](https://github.com/openjavaformat/open-java-format/pull/232), [#257](https://github.com/openjavaformat/open-java-format/issues/257)).
- The Gradle plugin writes the `.idea` files it changes as IntelliJ IDEA writes them, so the IDE's next save no longer rewrites them, and an empty `min-version` in `externalDependencies.xml` no longer fails the task ([#262](https://github.com/openjavaformat/open-java-format/issues/262), [#266](https://github.com/openjavaformat/open-java-format/pull/266)).
- Format in an Eclipse Java editor wraps a long string in the selection, as `--character-ranges` does ([#235](https://github.com/openjavaformat/open-java-format/pull/235)).

## Library

- `Formatter.getFormatReplacements`, `Input.getPositionTokenMap` and `SnippetFormatter.format` return `java.util.List` and Guava's `RangeMap` instead of `ImmutableList` and `ImmutableRangeMap`, so code compiled against 21.0.2 that calls them has to be compiled again. `FormatterService` in the SPI is unchanged ([#202](https://github.com/openjavaformat/open-java-format/issues/202), [#218](https://github.com/openjavaformat/open-java-format/pull/218)).
